# 82 · 把当前系统做成可分发的刷机包（J716F · Arch + Steam Game Mode）

日期：2026-11-10
目标设备：Lenovo Xiaoxin Pad Pro 2021（TB-J716F，SM8250-AC / 骁龙 870 / 8G+128G，aarch64）
当前系统：Arch Linux ARM，内核 6.13.0-sm8250 #26，greetd → gamescope → Steam Big Picture，救援系统在 `sda17`（ARCHRESCUE）

---

## 0. 结论（先看这段）

1. **本机没有原生 TWRP，但"卡刷"可以自己造**：
   - **线刷**（fastboot，PC）仍是首次安装/救砖的唯一入口——详见本文；
   - **卡刷**有两种形态：① 标准 **TWRP 兼容 zip**（给有 TWRP/以后移植 TWRP 的场景）；② **自建 mini-recovery 卡刷**（recovery 镜像写进空闲的 `recovery_a/b`，用 `misc` 的 BCB command 从系统内重启进入，从 SD/USB 读 `/j716f` payload，全程不需要 PC）——详见 `docs/84-线刷卡刷双路线.md`。**mini-recovery 与 SD 卡刷写已在本机实测跑通（2026-11-10）**，rootfs 整盘重装待补镜像。
   一句话：**线刷负责"从零到能用"，卡刷负责"日常更新/重装/修系统"**。
2. 你的"系统"只有两层需要发布：
   - `boot_a` / `boot_b`（各 96 MiB）里的 Android boot 镜像：kernel + DTB + 定制 busybox initramfs（实际 35.4 MB）；
   - `sda18`（PARTLABEL=userdata，108.25 GiB，exact 116,237,611,008 B，ext4）里的 Arch 根文件系统。
   其余分区（persist、modem、modemst1/2、fsg、bt、devinfo、uefivarstore、cdt…）是**设备唯一数据，绝不发布、绝不覆盖**。
3. 推荐发布形态：**一键线刷包** = `boot.img` + `rootfs.simg`（Android sparse 格式，约 10–15 GB）+ Windows 安装脚本 + 文档 + SHA256。用户操作 = 解锁 BL → 装 USB 驱动 → 双击脚本 → 等 10–20 分钟。
4. **不要做全盘/QFIL/EDL 包**：会覆盖设备唯一校准/基带数据；而且本机 EDL 从未落地验证（docs/81 §1.6），没有 9008 兜底。保底永远是 fastboot 双槽 + 重刷 rootfs。
5. 发布前必须解决的 5 件事：
   - 交接收人的**解锁 BL 途径**（这是最大门槛，没解锁什么都刷不了）；
   - **彻底清个人数据**（SSH 私钥、WiFi 密码、蓝牙配对、Steam 登录态、bash history、`lan_common.py` 里的明文密码…）；
   - **首启脚本**（machine-id / SSH host key / 扩分区 / 关键：写 `/.boot-ok`，否则新机 3 次重启后被 init 判失败）；
   - **ABL 槽位计数**（约 7 次重启进 fastboot）：**已有免 PC 解决思路**——Qualcomm 的 A/B 状态在 GPT 分区属性位里，Linux 可写；用 qbootctl 每次启动 `-m` 标记成功即可，详见 `docs/83-ABL计数彻底解决.md`（仍待真机验证）；
   - **法务**（内核 GPLv2 源码、Steam 客户端/账号不可再分发、高通固件专有、联想原厂文件不可分发）。
6. 只想给一两个朋友用 → 完整包没问题；想公开发到网上 → 改发"精简包 + 首启联网装 Steam"或"只发构建配方/脚本"，风险低一个数量级。

## 1. 当前系统的分层与发布边界

| 层 | 内容 | 位置/大小 | 是否发布 |
|---|---|---|---|
| 引导器 | ABL / XBL / TZ / hyp / keymaster / devcfg / vbmeta | `sdb`、`sdc`、`sde`（1–16 等） | **不动、不发布** |
| 启动镜像 | Android boot.img v2（kernel + vendor ramdisk + DTB），双槽同一镜像 | `boot_a=/dev/sde11`、`boot_b=/dev/sde34`，各 96 MiB，实际 35,405,824 B | **发布**（`boot.img`） |
| 根文件系统 | Arch Linux ARM + gamescope + Steam + FEX + 定制服务 | `sda18`（userdata）108.25 GiB ext4，label `ubuntu-j716f`，已用约 38 G | **发布**（清理后的 `rootfs.simg`） |
| 救援系统 | ARCHRESCUE 最小 Arch（init 优先找 sda17） | `sda17`（原 `super`，8 G） | v1 **不发**；别人机器上 sda17 还是原厂 super，发了也要额外刷 |
| 设备唯一数据 | persist、modemst1/2、fsg/fsc、bluetooth、devinfo、uefivarstore、cdt、apdp、msadp… | 多个分区 | **绝不发布、绝不覆盖** |
| Steam 游戏库 / SD 卡 | 用户自己的游戏 | microSD / home | 不发布 |

启动链（决定发布包必须怎么设计）：

```
ABL → boot_a/boot_b（Android boot.img：kernel + 定制 initramfs + DTB）
     → initramfs /init：按 /dev/sda18 → /dev/sd*18 → by-partlabel/userdata → /dev/sda17
       → /dev/sd*17 → /dev/sda* → /dev/mmcblk0p* 找 ext4 根
     → mount → switch_root → systemd → greetd → gamescope → Steam
```

两个必须知道的 initramfs 行为（`tools/init_patch.py`）：
- 主系统模式优先 `/dev/sda18`，找不到会尝试 `sda17` 和其它设备；
- 每次启动在根上写 `/.boot-count`，**若连续 3 次没有 `/.boot-ok`，就判定该根失败并回退**。发布镜像必须自带"启动成功写 `/.boot-ok`"的机制，否则新用户机器上 3 次重启后起不来（对方机器上 sda17 不是我们的救援系统，回退无处可去）。

## 2. 四种分发形态对比

| | A · 一键线刷包（推荐 v1） | B · 精简引导包 | C · 配方包（推荐公开版） | D · 全盘/QFIL 包 |
|---|---|---|---|---|
| 内容 | boot.img + 清理后 rootfs sparse 镜像 + install.ps1 + README | boot.img + 2–3 G 最小 rootfs，Steam/FEX 首启联网装 | 脚本 + 内核源码/补丁 + 配置 + 文档，无镜像或只含 boot.img | GPT + 全部分区 raw 镜像（EDL/QFIL） |
| 体积 | 约 10–15 G（7z 分卷 2 G/卷） | 约 2–4 G | 约 200–500 M | 约 120 G |
| 用户门槛 | 解锁 BL + Windows + 20 分钟 | 解锁 BL + 网络 + 30–60 分钟 | 会 Linux 编译/移植 | 9008 模式 + QFIL（未验证） |
| 离线可用 | ✅ | ❌（首启要网） | ✅ | ✅ |
| 法务风险 | 中（含高通固件；可去掉 Steam） | 低–中 | 最低 | 高（分发原厂/驱动文件） |
| 维护成本 | 每次更新重发 10–15 G | 中 | 低 | 极高 |
| 适用 | 朋友/小范围、要"开箱即用" | 公开下载 | GitHub 开源、可复现 | ❌ 不建议 |

**推荐组合**：v1 = A（先给自己/朋友，用来跑通流程和验证稳定性）；v2 = C（公开仓库）+ 网盘可选下载 A 的大文件。

> 判断标准：如果你不能保证"收包的人 100% 是 TB-J716F 且已解锁 BL"，就先只发 C，别发 A。

## 4. 制作流程（设备上操作，半天到一天）

> 下面命令都在平板上以 `player` 用户执行（`sudo` 提权）。产物放 `/home/j716f/release/`，最后再传到 PC。
> **前提**：设备确认是你要发布的那套系统（`uname -r`、`systemctl --failed`、Steam 能起）；先把当前状态记录/备份，别在打包途中改配置。

### 4.0 前置检查

```bash
uname -a
pacman -Q | wc -l
# 需要 android-tools 提供 img2simg，e2fsprogs 提供 mkfs/e2fsck，rsync 用于拷贝
pacman -Q android-tools e2fsprogs rsync
df -h /            # 需要 ≥ 40G 空闲（staging + 镜像 + sparse 文件）
```

### 4.1 冻结基线（只读记录，不发布）

```bash
R=/home/j716f/release; mkdir -p "$R"
{ uname -a; echo; cat /etc/os-release; echo; pacman -Q; echo;
  systemctl list-unit-files --state=enabled; echo; lsblk -o NAME,SIZE,FSTYPE,PARTLABEL,LABEL; } > "$R/manifest.txt"
sha256sum "$R/manifest.txt"
# 当前 boot 分区（96 MiB）内容
sudo dd if=/dev/disk/by-partlabel/boot_a of="$R/boot-from-device.img" bs=1M count=96 status=progress conv=fsync
sha256sum "$R/boot-from-device.img"
```

### 4.2 得到 `boot.img`

优先级 1：**直接使用当前跑着的 boot 分区内容**（最保真），然后把结尾填充截掉：

```bash
python3 - "$R/boot-from-device.img" <<'PY'
import struct, sys
d = open(sys.argv[1],'rb').read()
assert d[:8] == b'ANDROID!', '不是 Android boot 镜像'
ks,ka,rs,ra,ss,sa,ta,ps,hv,ov = struct.unpack_from('<10I', d, 8)
dtbsz = struct.unpack_from('<I', d, 1648)[0]
a = lambda x: (x + ps - 1)//ps*ps
total = ps + a(ks) + a(rs) + a(ss) + a(dtbsz)
print('valid length =', total)
open(sys.argv[1]+'.len','w').write(str(total))
PY
truncate -s "$(cat "$R/boot-from-device.img.len")" "$R/boot-from-device.img"
cp "$R/boot-from-device.img" "$R/boot.img"
sha256sum "$R/boot.img"
```

优先级 2：用 PC 上已验证的 `backup/boot-main.img`（35,405,824 B，cmdline 干净：只有 `pstore.kmsg_bytes=131072 loglevel=7`）——同样需确认它与当前 `/lib/modules` 内核版本配套（本地镜像 kernel 34,011,648 B，ramdisk 1,244,402 B，DTB 141,534 B）。

**⚠️ 不要误用带 mask 的镜像**：`backup/boot-stable.img` 和 `backup/boot-btfix.img` 的 cmdline 里有
`systemd.mask=j716f-gamemode.service systemd.mask=j716f-gamemode-bootstrap.service`（当初为稳定测试加的），
用它发布会导致**开机不进 Steam，只停在控制台**。发布前务必检查：

```bash
python3 - "$R/boot.img" <<'PY'
import sys
d = open(sys.argv[1],'rb').read()
print(d[64:64+512].split(b'\x00')[0].decode())
PY
# 期望只有：pstore.kmsg_bytes=131072 loglevel=7（不能出现 systemd.mask=j716f-gamemode*）
```

如果当前 boot 分区里确实带了 mask，去掉即可（解包 → 改 cmdline → 重打包，或直接用 `backup/boot-main.img`）。已解锁设备的 ABL 不校验 header id，改 cmdline 是安全的（历史上 `tools/build_boot_stable.py` 就是这么做的）。

**其它注意**：
- 不要在发布包里用实验性 DTB（3.19 GHz OPP、670 MHz GPU 之类）。用 docs/75 稳定基线的镜像。
- boot.img 与 rootfs 必须配套：rootfs 内 `/lib/modules/<kernel>`、`/lib/firmware` 必须对应这个 boot 镜像的内核版本。

### 4.3 制作干净 rootfs 镜像（核心步骤）

**绝对不要** `dd if=/dev/sda18` 整盘：108 G 里含 38 G 你的私人数据、swapfile、游戏、日志，且会有大量空洞，既泄露隐私又巨大。

正确做法：新建一个 ext4 镜像文件，把系统"复制"进去并清理：

```bash
R=/home/j716f/release
IMG=$R/rootfs.img
# 逻辑大小 = 目标 userdata 分区大小（116,237,611,008 B）；先用精确值，避免首启再 expand
truncate -s 116237611008 "$IMG"      # 稀疏文件，实际占用随写入增长
mkfs.ext4 -L J716F-ROOT -m 1 -E lazy_itable_init=0,lazy_journal_init=0 "$IMG"
mkdir -p /mnt/j716f-img
sudo mount -o loop "$IMG" /mnt/j716f-img

# 从运行中的系统拷贝（排除清单见 §5）
sudo rsync -aHAX --numeric-ids \
  --exclude=/proc --exclude=/sys --exclude=/dev --exclude=/run \
  --exclude=/tmp --exclude=/var/tmp --exclude=/mnt --exclude=/media \
  --exclude=/home/j716f/docs --exclude=/home/j716f/backup --exclude=/home/j716f/j716f-linux \
  --exclude=/home/j716f/tools --exclude=/home/j716f/release --exclude=/home/j716f/.cache \
  --exclude=/home/j716f/.ssh --exclude='/home/j716f/.local/share/Steam' \
  --exclude='/home/j716f/.steam' --exclude=/home/j716f/SteamLibrary \
  --exclude='/home/j716f/Steam' \
  --exclude='/var/cache/pacman/pkg' --exclude=/var/log/journal \
  --exclude='/swapfile' --exclude=/opt/steam-arm --exclude=/opt/fex-rootfs \
  / /mnt/j716f-img/

# 在镜像里清理（§5 清单），改 fstab、加首启服务
```

> `--exclude=/opt/steam-arm`、`--exclude=/opt/fex-rootfs` 是"干净包"的选择：Steam 客户端（Valve SSA）与 FEX rootfs 不随包分发，改由首启脚本联网安装。想发"开箱即用"完整包就不排除这两项，但法务风险高、体积大。

镜像内要做的改造：

1. **fstab 根改成标签**（不要带旧 PARTUUID）：
   ```bash
   sudo sed -i -E 's|^[^#[:space:]]+[[:space:]]+/[[:space:]]+ext4|LABEL=J716F-ROOT / ext4|' /mnt/j716f-img/etc/fstab
   sudo sed -i '/swapfile/d' /mnt/j716f-img/etc/fstab
   ```
2. **身份重置**：
   ```bash
   sudo truncate -s 0 /mnt/j716f-img/etc/machine-id
   sudo rm -f /mnt/j716f-img/var/lib/dbus/machine-id /mnt/j716f-img/etc/ssh/ssh_host_*
   sudo rm -rf /mnt/j716f-img/home/j716f/.ssh /mnt/j716f-img/home/j716f/.bash_history /mnt/j716f-img/root/.bash_history
   ```
3. **默认账号**：保留用户名 `player`（大量脚本和 systemd 单元硬编码 `/home/j716f/…`，改名成本高、风险大），设默认密码并强制首登修改：
   ```bash
   sudo chroot /mnt/j716f-img /usr/bin/env sh -c 'echo "player:j716f" | chpasswd; chage -d 0 player'
   ```
   并在 README 写明默认密码与修改方法。
4. **首启服务**（见 §4.4），必须包含写 `/.boot-ok` 的逻辑。
5. 收起镜像：
   ```bash
   sudo umount /mnt/j716f-img
   e2fsck -f -y "$IMG"
   img2simg "$IMG" "$R/rootfs.simg"      # Android sparse，fastboot 原生支持
   rm -f "$IMG"                          # 稀疏镜像已生成，删除中间文件省空间
   sha256sum "$R/rootfs.simg"; ls -lh "$R/rootfs.simg"
   ```

> 如果设备上空间不够：先 `rm -rf /home/j716f/release/rootfs.img` 再 `img2simg`（需另备镜像所在分区空间），或者把 `rootfs.img`/`rootfs.simg` 直接生成到 microSD 上。

### 4.4 首启服务（发布包必须自带）

`/etc/systemd/system/j716f-firstboot.service`：

```ini
[Unit]
Description=J716F first boot setup
ConditionPathExists=!/var/lib/j716f-firstboot.done
After=local-fs.target
Before=display-manager.service
Wants=network-pre.target

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/j716f-firstboot.sh
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
```

`/usr/local/sbin/j716f-firstboot.sh`（要点）：

```bash
#!/bin/bash
set -e
# 1) 扩展根到分区实际大小（镜像逻辑大小可能小于目标分区）
ROOTDEV=$(findmnt -n -o SOURCE /)
resize2fs "$ROOTDEV" || echo "resize2fs skipped"
# 2) 生成设备身份
[ -s /etc/machine-id ] || systemd-machine-id-setup
ssh-keygen -A
hostnamectl set-hostname j716f
# 3) 默认密码只在没改过时设置
chage -l player | grep -q 'password must be changed' || true
# 4) 可选：从 SD 卡 U 盘读配网文件（见 README）
#    /dev/disk/by-label/J716F-SETUP 内 wifi.txt: SSID=... / PSK=...
# 5) 写启动成功标记（initramfs 连续 3 次找不到它就会回退）
touch /.boot-ok
touch /var/lib/j716f-firstboot.done
```

再补一个每次启动都兜底写 `/.boot-ok` 的单元（更稳）：

```ini
# /etc/systemd/system/j716f-boot-ok.service
[Unit]
Description=Mark boot successful for initramfs watchdog
After=multi-user.target
[Service]
Type=oneshot
ExecStart=/usr/bin/touch /.boot-ok
[Install]
WantedBy=multi-user.target
```

启用：`systemctl enable j716f-firstboot.service j716f-boot-ok.service`（chroot 里用 `systemctl --root` 或建软链）。

### 4.5 Windows 安装器（`install.ps1`）

流程与校验（伪代码）：

```
1. 要求 Windows 10/11 x64，管理员权限（装 USB 驱动需要）
2. fastboot devices                     # 必须有且只有一台
3. fastboot getvar product              # 记录；与 manifest 的 device 匹配，否则中止
4. fastboot getvar partition-size:userdata
   # 必须 == 0x1b104d3000（116,237,611,008 B），或 ≥ rootfs 逻辑大小，否则中止（防刷错机型/分区表）
   # 参考：boot_a/boot_b = 0x6000000（100,663,296 B）
5. fastboot getvar unlocked             # 必须是 yes
6. 二次确认：屏幕提示"将清空平板全部数据（含原 Android/userdata），不可恢复"
7. fastboot flash boot_a images/boot.img
8. fastboot flash boot_b images/boot.img
9. fastboot flash userdata images/rootfs.simg    # 关键一步，见 §7 风险
10. fastboot set_active a               # 显式重置 ABL 槽位计数
11. fastboot reboot
12. 输出日志到 install-log.txt；失败时明确告诉用户"停手、别继续刷其他分区、把日志发出来"
```

注意：
- `fastboot flash userdata` 在本机**尚未实测**，发布前必须在真机上验证一次；如果 ABL 拒绝（`FAILED (remote: ...)`），v1 就得改走"救援系统 + 网络/SD 写盘"方案（见 §7）。
- 镜像已经是 sparse（`rootfs.simg`），不要再加 `-S` 拆包；`-S` 只对 raw 镜像有意义。
- 安装器不要内置任何账号，也不要尝试改 `devinfo`/`misc` 之外的任何分区。

### 4.6 实测（发布门槛，不做完不许发）

至少在一台**从原厂 Android 全新状态、仅解锁 BL** 的 TB-J716F 上跑完整流程（自己的机器也行，但需先确认全量备份可恢复）。测试项见 §6。

## 7. 风险与边界

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 刷错机型（不是 TB-J716F） | 中 | 可能变砖 | 安装器校验 `product` + `partition-size:userdata`；README 大红字 |
| **EDL/9008 未验证** | — | 没有最终兜底 | 发布前实测或明确写"无 EDL 兜底"；保底 = fastboot 双槽 + 重刷 rootfs |
| `fastboot flash userdata` 被 ABL 拒绝或太慢 | 中 | 方案 A 不可用 | **发布前先实测**；失败则退到"刷救援 boot → 网络/SD 卡写 sda18"或只发 C 方案 |
| ABL 槽位计数耗尽（约 7 次重启进 fastboot） | 高 | 用户以为变砖 | **已实测解决（2026-11-10）：qbootctl 每启动 `-m` 标记成功，连续重启不再递减（docs/83）**；发布包装机即预置该服务。兜底：mini-recovery 自修（docs/84）、手机 OTG fastboot、PC 看门狗 |
| 新机没有 `/.boot-ok`，3 次启动后回退 | 中 | 无法开机 | 首启服务 + 每次启动兜底写标记；实测重启 3 次以上 |
| boot.img 与 rootfs 内核/模块不配套 | 中 | 黑屏/驱动全失效 | manifest 锁定 kernel 版本与 sha256；成对发布 |
| rootfs 小于目标 userdata 分区 | 低 | 空间浪费 | 首启 `resize2fs` |
| 分区表/大小不同（同型号不同批次） | 低 | 镜像写坏 | 安装器校验分区大小；只支持 exact 型号 |
| 超频/热控不稳定 | 中 | 黑屏/硬复位 | 用 docs/75 稳定基线，不带 3.19 GHz/670 MHz 实验项 |
| 无键盘无法配网 | 中 | 用户卡在首启 | SD 卡 `J716F-SETUP/wifi.txt` 预置方案；README 写清 |
| Steam 更新破坏 gamescope/FEX 兼容 | 中 | 黑屏 | 记录已验证版本；提供回滚说明；不要打包 Steam 时更明显 |

## 8. 法务与合规

1. **Linux 内核 GPLv2**：你发布的 boot.img 和 rootfs 含内核/模块二进制，必须提供对应源码（或书面 offer）。可用：
   - `backup/kernel-src.tar.gz`（364 MB，`restore/home/j716f/j716f-linux`）、`docs/j716f-ubuntu/patches_kernel_linux-6.15.11-j716f-530.patch` + `configs_kernel_j716f-6.15.11.config`；
   - 建议开一个 GitHub 仓库存 kernel tree + .config + patches，发布页附链接（`NOTICE-SOURCE.md`）。
2. **Steam 客户端**：Valve Steam Subscriber Agreement 不允许再分发客户端文件；**不要**打包 `/opt/steam-arm`、`~/.steam`。改为首启/用户自行从官方渠道安装（Steam-ARM 的下载脚本从 Valve CDN 拉取）。Steam **账号绝不能**带。
3. **高通固件**（`/lib/firmware/qcom/*`：ADSP/CDSP/WCN6855/Adreno 等）：专有文件，严格说不可再分发。两种做法：
   - 更稳妥：发布"从本机原厂分区提取固件"的脚本（用户自己的设备，自己提取）；
   - 务实：随包发布但明确来源与自担风险（社区 ROM 的常规做法，法律上仍有灰区）。
4. **联想原厂文件**（原厂 boot、super、vendor、Android 固件）：不可再分发；`optional/stock-boot.img` 只在你确认有权时提供，否则改为"从官方固件包提取"说明。
5. **其它组件**：gamescope / MangoHud / BlueZ / Mesa / FEX / Arch 包各自许可证，保留 `/usr/share/licenses`；附第三方声明。
6. **个人信息保护**：包内不得有他人数据；发布前跑 §5.3 抽查。不要提供付费刷机服务、不内置他人账号。

## 10. 需要先定的决策

1. **受众**：只给一两个朋友（完整包 A）还是公开发布（C 或 B）？
2. **Steam**：打不打包？（打包 = 方便但法务灰；不打 = 首启联网装，首次使用多 10–30 分钟）
3. **形态**：A 一键线刷 / B 精简+首启下载 / C 只发配方？
4. **是否放弃 Android**：刷 userdata 等于清掉原 Android，回退需要原厂固件；接受吗？
5. **维护**：以后内核/Steam 更新后谁重打包、发新版本？
6. 是否需要我把 §4 的流程落成 `release/` 目录（`build-rootfs.sh`、`firstboot.sh`、`install.ps1`、README 模板、NOTICE 模板）？

> 最小验证路径（建议先做）：先只做**自用备份包**——用 §4 生成 boot.img + rootfs.simg，在自己的设备上验证"刷进去能开机"（先 `fastboot flash boot_b` 试、`fastboot boot` 临时启动更安全），确认 `fastboot flash userdata` 可行后，再决定要不要给别人。
