### 2.2 BlueZ 5.87（原生）

- 因此“5.87 用了不同扫描参数/扩展扫描”不是根因。

  - 原版模块 + `btmgmt find -l` 正常发现设备；
- **结论：该补丁方案无效/有 bug，已回滚，不能再用于“修复”**。

### 2.4 控制器存储状态
`/var/lib/bluetooth/AA:BB:CC:DD:EE:FF/AA:BB:CC:DD:EE:FF/info`：
```
AddressType=public
SupportedTechnologies=LE;
Trusted=true
WakeAllowed=true
Services=...1800;...1801;...180a;...180f;...1812;...ae00
```
- 控制器是 **LE HID（HOG）**，public 地址；
- `WakeAllowed=true` 对应 BlueZ 5.87 的 `DEVICE_FLAG_REMOTE_WAKEUP`。

### 2.5 内核拒绝 REMOTE_WAKEUP flag
dmesg 每次启动都有：
```
Bluetooth: hci0: Bad flag given (0x1) vs supported (0x0)
```
- 源码 `net/bluetooth/mgmt.c`：`supported_flags = hdev->conn_flags`；
- 当前 `conn_flags=0`，不支持 `HCI_CONN_FLAG_REMOTE_WAKEUP`；
- BlueZ 5.72/5.87 都会尝试写 `WakeAllowed`（5.72 也会，因为存储里有 WakeAllowed），所以这条 warning 不是 5.87 独有，但 **5.87 更积极处理 WakeAllowed/auto-connect**。

### 2.6 BlueZ 5.87 与 5.72 源码差异（相关点）
- `device_set_auto_connect()`：
  - 5.72：`if (!device->le || device_address_is_private(device)) return;`
  - 5.87：只检查 `!device->le`，**允许 private 地址进入 auto-connect**；随后对 private 地址再检查并 `return`（逻辑位置不同）；
- 5.87 增加了更多 `device_set_auto_connect()` 调用点（连接/配对/服务状态变化时）；
- 5.87 增加 `WakeAllowed` 持久化/`DEVICE_FLAG_REMOTE_WAKEUP` 逻辑；
- 两者扫描参数、Discovery 主流程高度相似；**差异集中在 auto-connect 列表/后台扫描/设备 flags**。

## 7. 已找到并验证根因：`WakeAllowed=true`（2026-11-08 13:20）

### 根因
- 内核 6.13 的 QCA6390 `hdev->conn_flags=0`，**不支持 `HCI_CONN_FLAG_REMOTE_WAKEUP`**；
- BlueZ 5.87 对控制器存储里的 `WakeAllowed=true` 会尝试设置 REMOTE_WAKEUP（dmesg `Bad flag given (0x1) vs supported (0x0)`）；
- 该失败/重试状态与 5.87 的 background scan/auto-connect 交互，导致 `LE Set Scan Parameters EBUSY`，进而 QCA6390 固件 hard reset（多次复现）。

### 验证结果
| 测试 | 结果 |
|---|---|
| 5.87 + 空 storage | 扫描正常，无复位 |
| 5.87 + 控制器 `Trusted=true, WakeAllowed=true` | 启动/扫描 EBUSY / hard reset |
| 5.87 + 控制器 `Trusted=true, WakeAllowed=false` | **扫描正常，无复位**（T2） |
| 5.87 + `WakeAllowed=false` + 控制器连接 + 扫描 | **扫描正常，无复位**（T3） |
| 重启后 | 5.87 自动启动、控制器自动 Connected、`WakeAllowed=no`、无 hard reset |

### 当前实现
- 启用 Arch 原生 **BlueZ 5.87**（`bluetooth.service` enabled）；
- 禁用 BlueZ 5.72 服务；
- `/usr/local/bin/bluetoothctl` → 5.87；
- 控制器 storage：`Trusted=true`、**`WakeAllowed=false`**；
- `j716f-bt-reconnect.service` 改为依赖 `bluetooth.service`；
- 重启后控制器自动连接（input/hidraw 正常）。

### 待完善
1. **新设备配对**：新设备可能默认 `WakeAllowed=true`，需在配对后强制设为 false（脚本/服务/BlueZ 补丁）；
2. **Steam UI**：切换/重启后曾出现 logo 转圈（CEF assert），需确认当前是否正常并修复；
3. 长期测试：WiFi 共存、休眠唤醒、反复连接/扫描；
4. 更新 `j716f-bt` helper/文档为 5.87 路径。

## 11. 原生 5.87 的 BlueZ 扫描补丁尝试与最终回退（2026-11-08 13:55）

- 发现 5.87 的 `bluetoothctl scan` 使用 **`MGMT_OP_START_SERVICE_DISCOVERY`**（0x003a），而 `btmgmt find` 用普通 `Start Discovery`（0x0023）；
- 已从 BlueZ 5.87 源码打补丁：过滤发现也强制走 `MGMT_OP_START_DISCOVERY`，重新编译 `bluetoothd` 并替换测试；
- 结果：**第一次 scan 仍 hard reset**（uptime 清零），说明 5.87 的扫描不稳定不只在 service-discovery 路径；
- 已恢复原版 5.87 二进制（备用），并回退 **BlueZ 5.72**。
- 最终：**Steam UI 的扫描/配对使用 5.72**；5.72 连续 3 次扫描 + WiFi 稳定（客户端 segfault 是已知现象，守护进程正常）。
- 原生 5.87 若要继续，需要更深入的 BlueZ/HCI 差异分析，不建议在稳定系统上反复试。
