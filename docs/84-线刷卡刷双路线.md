# 84 · 线刷 + 卡刷双路线（TWRP 兼容 zip 与 J716F 自建 mini-recovery）

日期：2026-11-10
关联：`docs/82`（发布包总体方案）、`docs/83`（ABL 计数免 PC 方案）

---

## 0. 结论（先看这段）

1. **线刷**（fastboot，PC）负责：首次安装、救砖、装 recovery、装 qbootctl 服务。这是"从零到能开机"的唯一入口。
2. **卡刷**（zip，无 PC）负责：日常更新、重装、修系统。但 J716F 原生没有 TWRP，所以卡刷要分两种形态：
   - **A · TWRP 兼容 zip**：按 TWRP 规范打包（`META-INF/com/google/android/update-binary` + payload），给"有 TWRP 或以后移植了 TWRP"的场景；同一份 zip 也能被我们自己的 mini-recovery 执行。
   - **B · mini-recovery 卡刷（本机现实路线）**：把自定义 recovery 镜像写进空闲的 `recovery_a/recovery_b`（各 100 MiB），用 `misc` 的 BCB command `boot-recovery` 从系统内重启进去（或按键组合，待实测），recovery 从 SD/USB 读 zip 自动安装。**全程不需要 PC。**
3. **系统内更新**（U 路线）：内核写 `boot_b` + `qbootctl` 切槽（失败回滚 `boot_a`）；rootfs 用 pacman/rsync。这依赖 docs/83 的 qbootctl。
4. 建议发布时同时提供：线刷包（首次用）+ 卡刷 zip（更新用）+ recovery 镜像（装一次，长期用）。

---

## 1. 三种包的分工

| | L · 线刷包 | A · TWRP 兼容 zip | B · mini-recovery 卡刷 | U · 系统内更新 |
|---|---|---|---|---|
| 通道 | PC + fastboot | TWRP / 任意 recovery | 本机 recovery_a/b | 运行中的系统 |
| 需要 PC | 是（首次/救砖） | 否（设备已有 TWRP） | 否 | 否 |
| 内容 | boot.img + rootfs.simg + install.ps1 + （可选）recovery.img | boot.img + rootfs.img.gz + update-binary | 同 A（可共用） | 内核包 / rootfs 增量 |
| 适用 | 首次安装、救砖、装 recovery | 有 TWRP 的设备/以后移植 | 日常更新、重装、修槽 | 小版本更新 |
| 风险 | 中（fastboot flash userdata 未实测） | 中（依赖 TWRP 环境） | 中（recovery 需先装好） | 低（boot A/B） |

## 2. 线刷包（首次安装 / 救砖）

完整设计见 `docs/82` §3–§4。这里只强调与"卡刷"相关的部分：

1. 首次线刷时**顺便把 recovery 与 qbootctl 一起装好**，之后用户就再也不需要 PC：
   - `fastboot flash recovery_a images/recovery.img`
   - `fastboot flash recovery_b images/recovery.img`
   - 系统首启后安装 `j716f-mark-success.service`（docs/83）
2. 安装器仍然是：`boot_a` + `boot_b` + `userdata`，不动 `persist/modem/modemst*/fsg/xbl/abl/vbmeta/devinfo` 等。
3. 如果 `fastboot flash userdata` 被 ABL 拒绝，改走：
   - 先刷 `boot-recovery.img` 到 `boot_a`（临时）→ 进 recovery → 从 SD 卡把 `rootfs.img.gz` 写到 userdata → 再刷回正常 `boot.img`；
   - 或者用 `fastboot boot` 临时启动一个"安装器 boot 镜像"（不写槽），从 USB 网络/SD 安装。

## 3. 卡刷包 A：TWRP 兼容 zip

### 3.1 适用条件与边界

- TWRP 生态的"卡刷"= 在自定义 recovery（TWRP）里刷 zip。**TB-J716F 目前没有公开 TWRP**（docs/82 已核实），所以这条路是为两种情况准备：
  1. 以后有人（你或社区）为 J716F 编出 TWRP；
  2. 同 SoC/同分区布局的其它设备，或你把它当模板。
- **不要**把这种 zip 当作"所有 Android 设备通用"——`update-binary` 里要写死设备校验与分区名。
- 我们自己的 mini-recovery 也会按同样规范执行 `update-binary`，所以 **A 和 B 可以共用一个 zip**。

### 3.2 zip 结构

```
j716f-arch-steam-<ver>-cardflash.zip
├─ META-INF/com/google/android/update-binary   # 入口脚本（TWRP 会执行它）
├─ META-INF/com/google/android/updater-script  # 仅为兼容某些 recovery 的占位（见 3.4）
├─ payload/manifest.json
├─ payload/SHA256SUMS
├─ payload/boot.img                            # 35.4 MB
├─ payload/rootfs.img.gz                       # 清理后的 ext4 镜像，gzip（约 5–10 GB）
└─ payload/qbootctl                            # 静态 aarch64（musl static），用于 A/B 标志
```

> 备选：用 `rootfs.tar.gz` + `mke2fs/tar` 代替 `rootfs.img.gz`——体积更小，但要求 recovery 里有可用的 `mke2fs`/`tar`（TWRP 通常有；自建 recovery 要自己塞）。**首次实现建议用 `rootfs.img.gz` + `gunzip|dd`，依赖最少。**

### 3.3 `update-binary` 完整示例（可直接改）

```sh
#!/sbin/sh
# TWRP / mini-recovery 通用卡刷脚本
# 参数: $1=API 版本  $2=命令管道 fd  $3=zip 路径
OUTFD="$2"; ZIP="$3"

ui_print() { echo "ui_print $1" >&"$OUTFD"; echo "ui_print" >&"$OUTFD"; }
abort() { ui_print "错误: $1"; ui_print "已中止，未完成任何改动（如需恢复见 README）"; exit 1; }
part() {  # 解析分区路径：TWRP 用 by-name，我们的 initramfs 用 by-partlabel
    for p in "/dev/block/by-name/$1" "/dev/disk/by-partlabel/$1"; do
        [ -e "$p" ] && { echo "$p"; return 0; }
    done
    return 1
}

ui_print "J716F Arch + Steam Game Mode 卡刷包"
ui_print "设备: $(getprop ro.product.device 2>/dev/null || echo unknown)"

# 1) 设备校验（本机 cmdline 含 j716f / p11_pro_plus）
cat /proc/cmdline | tr ' ' '\n' | grep -qiE 'j716f|p11_pro_plus' \
    || abort "不是 Lenovo TB-J716F（cmdline 不匹配）"

# 2) 解出 payload
TMP=/tmp/j716f_payload
rm -rf "$TMP"; mkdir -p "$TMP"
unzip -o "$ZIP" 'payload/*' -d /tmp >/dev/null 2>&1 || abort "解压 payload 失败"
cd "$TMP/payload" || abort "payload 目录不存在"

# 3) 校验
sha256sum -c SHA256SUMS || abort "payload 校验失败（文件损坏或不是原包）"

# 4) 写 boot（A/B 双槽同镜像，防止回退踩空）
BOOT_A=$(part boot_a) || abort "找不到 boot_a"
BOOT_B=$(part boot_b) || abort "找不到 boot_b"
ui_print "写入 boot_a / boot_b ..."
dd if=boot.img of="$BOOT_A" bs=4M conv=fsync || abort "写 boot_a 失败"
dd if=boot.img of="$BOOT_B" bs=4M conv=fsync || abort "写 boot_b 失败"

# 5) 写 rootfs 到 userdata（会清空数据！）
USERDATA=$(part userdata) || abort "找不到 userdata"
ui_print "写入根文件系统（约需 10–20 分钟，请勿断电）..."
gunzip -c rootfs.img.gz | dd of="$USERDATA" bs=4M conv=fsync || abort "写 userdata 失败"

# 6) A/B 标志：只标记成功（已实测；不要在这里用 -s 切槽，见 docs/83 §6）
[ -x ./qbootctl ] && chmod +x ./qbootctl
if [ -x ./qbootctl ]; then
    ui_print "标记 A/B 槽位状态 ..."
    ./qbootctl -m >/dev/null 2>&1 || ui_print "警告: qbootctl -m 失败（不影响开机，但重启计数仍会走）"
fi

ui_print "完成。重启后首次开机需配网。"
exit 0
```

要点：

- `ui_print` 输出到 TWRP 的 fd；我们的 mini-recovery 也要实现同名 fd 协议（或简化：直接写 tty0，见 §4.2）。
- `rootfs.img.gz` 的解压写入是**整盘覆盖**，等于清除原系统；如果只更新内核，用 §5 的 U 路线，别用这个。
- `qbootctl` 用 **static musl** 编译（TWRP 是 bionic 环境）：`meson -Ddefault_library=static` + musl-gcc，或直接交叉编译；实在不行，TWRP 里没有它也不影响开机，只是 ABL 计数问题会回来。
- **写 GPT 标志前必须先备份**（qbootctl 能回滚，但发布包不负责替用户备份）。

### 3.4 为什么不用 `updater-script`

- AOSP recovery 才解析 edify `updater-script`；TWRP 实际执行的是 `META-INF/com/google/android/update-binary`。
- 为了兼容极少见的老 recovery，可以放一个最小 `updater-script` 占位（内容 `# dummy`），但不要依赖它。
- 我们的 mini-recovery 也只实现 `update-binary` 的执行，不实现 edify。

### 3.5 签名与校验

- TWRP 默认不验证签名（可关），但**zip 里必须有 SHA256SUMS**，`update-binary` 自己 verify；这是真正防损坏/防篡改的一层。
- 对外发布时给 zip 本身附 `sha256`（README/Release 页），不要只依赖 zip 内部。

## 4. 卡刷包 B：J716F 自建 mini-recovery（本机现实路线）

### 4.1 为什么不做 TWRP

- TWRP 是 Android recovery，需要 AOSP 构建树 + 设备树 + sepolicy + HAL；为一个"跑 Linux/Steam 的平板"编 TWRP，投入产出比很低。
- 我们真正需要的只是：**能读写 boot/userdata 分区、能解压 payload、能跑 qbootctl 的最小 Linux 环境**。现有的定制 initramfs（busybox + telnetd + USB 网络）已经具备大半，扩展一下即可。

### 4.2 mini-recovery 镜像（已实现）

- 形式：和 `boot_a` 一样的 Android boot.img（kernel + initramfs + DTB），实际 **31.7 MB**，能塞进 100 MiB 的 `recovery_a/recovery_b`。
- 实现：以当前 `boot_a` 的 kernel/DTB 为底，替换 initramfs 的 `init`，加入：
  - `/recovery.sh`：主逻辑（日志、找介质、校验、刷写、标记、清 BCB、自动重启）；
  - `/bin/qbootctl`：**glibc static** 编译（`meson -Dc_args=-static -Dc_link_args=-static`），initramfs 里可直接跑；
  - `/etc/by-partlabel.map` + 启动时建 `/dev/disk/by-partlabel` 符号链接（initramfs 没有 udev，qbootctl 依赖这个目录）；
  - 90 秒看门狗（init 里后台 `sleep 90; reboot -f`），任何异常都不会把设备留在 recovery；
  - 保留 USB gadget（RNDIS + telnet）作高级调试通道。
- payload 布局（SD/U 盘根目录，FAT32 或 ext4 均可）：
  ```
  /j716f/SHA256SUMS      # 必须；不通过不写任何分区
  /j716f/boot.img        # 可选，写入 boot_a + boot_b
  /j716f/rootfs.img.gz   # 可选，整盘写 userdata（会清数据）
  /j716f/HOLD            # 可选，存在则不自动重启，停在 shell
  ```
- 逻辑（`recovery.sh`）：
  1. 挂 userdata（ext4）→ 日志写 `/recovery.log`（重启后可在系统里查看）；
  2. 扫描 `mmcblk0p*` / `sd[g-z]*`，避开内部 UFS 的 `sd[a-f]*`；
  3. 找到 `/j716f` 后按 SHA256SUMS 手工校验（兼容旧 busybox，不用 `sha256sum -c`）；
  4. 写 boot、可选写 rootfs、`qbootctl -m`、清 BCB、自动重启；
  5. 没找到 payload 就记日志 → 20 秒后自动重启回系统。

### 4.3 怎么进入 recovery

1. **软件方式（已实测可行）**：Android 标准 BCB 机制。往 `misc` 前 32 字节写 `boot-recovery`，ABL 下次启动会引导 recovery 分区。脚本：
   ```bash
   sudo python3 /home/j716f/tools/write_bcb.py --command boot-recovery
   ```
   只写 32 字节 + 自动备份 4 KiB 到 `/root/misc-head-backup-*.bin`；**已实测 Lenovo ABL 认这个 command**（见 §4.7），recovery 启动后会自己清掉 BCB，不会循环。
2. **按键方式（待实测）**：Lenovo 平板常见"音量加 + 电源"进 recovery；键盘/触屏不可用时作为备用。需要先在真机上试出组合键（可以刷一个显眼的 recovery 镜像后测试）。
3. 从 PC 强制：`fastboot reboot recovery`（ABL 支持的话）；或 `fastboot flash boot_a boot-recovery.img` 临时进 recovery（相当于用 boot 槽当 recovery）。

### 4.4 安装 recovery（首次线刷后从 Linux 装，无需 PC）

```bash
# 设备上（首次装或更新 recovery 镜像）
sudo /home/j716f/tools/install-mini-recovery.sh /home/j716f/deploy/boot-minirecovery.img
# 会自动备份 recovery_a/b 原内容到 /home/j716f/backup/

# 以后要重新构建 + 刷写：
sudo /home/j716f/tools/make-mini-recovery.sh --flash
```

之后系统内随时（两种等价写法）：
```bash
sudo /home/j716f/tools/reboot-to-recovery.sh
# 或
sudo python3 /home/j716f/tools/write_bcb.py --command boot-recovery
```

### 4.5 recovery 内的"卡刷"流程（用户视角，已实现）

1. 把 payload 拷到 SD 卡/U 盘的 `/j716f/` 目录（`SHA256SUMS` + `boot.img` + 可选 `rootfs.img.gz`）；
2. 平板运行 `write_bcb.py --command boot-recovery`（以后可做成 Steam 图标）；
3. 自动重启进 mini-recovery → 自动扫描介质 → 校验 SHA256 → 写 boot/rootfs → `qbootctl -m` → 清 BCB → 重启回系统；
4. 首次开机需要配网/登录 Steam（若刷了 rootfs 则数据被清空）。

> v1 的 mini-recovery 读的是**裸文件布局**（上面的 `/j716f/`），不是 zip；TWRP 兼容 zip 是给"有 TWRP 的环境"用的（§3），两者 payload 相同，由 `make-cardflash.py` 一次生成。

### 4.6 无 PC 的完整生命周期（已跑通前两步）

```
首次：PC 线刷（boot_a/b + userdata + recovery_a/b + qbootctl 服务）
  │
  ├─ 日常：系统内 pacman/Syu、Steam 更新（不碰 boot）
  ├─ 内核更新：新 boot 写 boot_a+boot_b（两槽同镜像）→ 重启；失败进 recovery 重写旧镜像
  ├─ 大版本/重装：SD 卡 payload → 重启进 recovery → 自动刷
  ├─ 系统起不来：同上传 recovery → 重装/修复
  └─ 极端：手机 OTG 或 PC fastboot（最后兜底）
```

## 5. 系统内更新（U 路线，依赖 docs/83 的 qbootctl）

### 5.1 内核更新（当前推荐：双槽写同一镜像）

> `qbootctl -s` 切槽**没有验证，而且实测发现它会覆盖 retry 位**（docs/83 §6），所以 v1 不做系统内切槽。

```bash
# 最稳：新内核同时写 boot_a 和 boot_b，两个槽永远同镜像（ABL 切槽也不会踩空）
sudo dd if=/home/j716f/deploy/boot-new.img of=/dev/disk/by-partlabel/boot_a bs=4M conv=fsync
sudo dd if=/home/j716f/deploy/boot-new.img of=/dev/disk/by-partlabel/boot_b bs=4M conv=fsync
sudo qbootctl -m          # 刷 boot 后 success 标志会被清，重新标记
sudo reboot
# 起不来：进 recovery 从 SD 写回旧 boot；或 PC fastboot 刷回
```

如果以后确实需要 A/B 两套内核（切槽），必须先在**备份 GPT** 的前提下单独实测 `qbootctl -s`（或改装 `qbootctl` 只切 active 位、保留 retry 位），确认 ABL 日志 retry count 不异常后再用。

### 5.2 rootfs 增量更新

- 常规：`pacman -Syu`（先做基线快照，见 docs/75）。
- 离线：SD 卡放 pacman 包/仓库，`pacman -U`；或用 rsync 覆盖 `/usr`、`/etc/j716f` 等（风险高，不如整盘重装）。

### 5.3 全量重装

- 用 §4 的 recovery + `rootfs.img.gz`（整盘覆盖），这是"卡刷"最标准的用法。

## 6. payload 设计与体积

| 方案 | 压缩后体积 | 依赖 | 备注 |
|---|---|---|---|
| `rootfs.img.gz`（整盘 ext4 镜像） | 约 5–10 GB | gunzip + dd | 最稳，推荐首发 |
| `rootfs.tar.gz` + mke2fs/tar | 约 4–8 GB | mke2fs + tar | 省一点，依赖更多 |
| 增量包（只含变更文件） | 几百 MB | rsync/tar | 后续优化项 |

发布渠道：GitHub Release 单文件 2 GB 限制 → 7z 分卷；或网盘 + `SHA256SUMS`。

## 8. 风险与注意

| 风险 | 说明 | 缓解 |
|---|---|---|
| BCB `boot-recovery` 不被 Lenovo ABL 识别 | 可能进不了 recovery | **已验证可用**（§4.7）；recovery 内会清 BCB，不会循环 |
| 按键组合未知 | 无键盘时无法操作 | 软件触发已验证；按键仍待测 |
| recovery 屏幕不亮 | 只能靠日志/自动流程 | 屏幕未验证；日志写 `/recovery.log`，流程自动完成并重启 |
| 整盘覆盖写 userdata 中断 | 系统不可用 | 重新进 recovery 重刷（幂等）；SD 卡保持包 |
| 覆盖原厂 recovery | 丢失原厂恢复能力（本来也没用） | 已备份 `recovery_a/b`（`/home/j716f/backup/recovery_*-before-*.img`） |
| qbootctl 静态二进制兼容性 | TWRP bionic 环境 | 用 glibc static（本机已验证）；TWRP 里未测 |
| `fastboot flash userdata` 未实测 | 线刷包可能不可用 | 先测；失败走 recovery + SD 方案 |
| 断电/低电量写 GPT | 分区表风险 | 写前确认电量 > 30%，用短命令 |
